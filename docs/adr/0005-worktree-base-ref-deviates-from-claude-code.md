# 副本基点以 Claude Code 的 `worktree.baseRef` 为基线，但在若干点上有意偏离

Worktree 开关原本只有一种建副本的方式：以主检出的本地 `HEAD` 为基点。主检出落后于远端
是很常见的状态——前一天没 pull、停在一个 feature 分支——于是「新会话的副本」实际上停在
旧提交上。用户以为新会话从最新代码开始，模型却基于陈旧代码修改，合并时才发现冲突或方向
错了。README 也没写这件事，唯一的提示是进入副本后守卫文案里那句「自己去 fetch + merge」，
那是事后补救，不是创建时的语义。

Claude Code 的 `worktree.baseRef` 已经把语义固定下来：默认 `fresh`，在创建副本前从
`origin` 拉默认分支，以拉到的提交为基点；`head` 则完全跳过网络，基于本地 `HEAD`，作为
「把未推送的工作带进副本」的逃生门。本插件在这四条上按原样对齐——默认 `fresh`、只取默认
分支（解析顺序 `refs/remotes/origin/HEAD` → `main` → `master`）、拉取有 5 秒上限、任何失败
都不阻断创建而是回退本地 `HEAD`；只有「有远端、找到了默认分支、fetch 没成功」这一种会在
开关的 hover 提示里标注「基点：本地 HEAD（远端未取到）」。下面三条不照抄，各有具体代价。

## 偏离清单

| 项 | Claude Code | dsh-worktree-switch | 为什么 |
|---|---|---|---|
| `FETCH_HEAD` 节流 | 24 小时内 `FETCH_HEAD` 被改写过就跳过 fetch，直接用本地提交 | 不节流：每次**真正创建副本**前都拉一次 | 我们的创建是人的显式动作（拨开关），不是 CLI 的启动路径；节流的可观测效果是「fresh 并不 fresh」——同一个仓库 24 小时内开第二个会话，副本静默停在旧提交上，而这正是本 ADR 要修的问题 |
| 命名 / 锁 / 清理 | 分支叫 `worktree-<name>`、`git worktree lock` 住、忽略 `**/.claude/worktrees/`、把项目设置复制进副本、`claude rm` 式回收 | 都不做：名字 = 分支 = 池内目录名，不加锁、不复制设置、不提供自动回收，丢弃只在面板上做两次确认 | 本插件的身份是「一份可用 `git worktree list` 认出来的普通 linked worktree」：池用 `.dsh/worktrees` 加 `.gitignore`，分支名可读即可；锁会把副本变成「必须由知道怎么解锁的人处理」的对象，而我们的丢弃语义是面板上的显式确认。复制项目设置则让「基点」从提交变成提交 + 现场环境，两种基点混在一起更难解释 |
| fetch 的执行位置 | CLI 进程内，天然就是用户的动作 | 宿主侧动作，绕过会话沙箱（会连网、会改写主检出的 remote-tracking ref，都不经过 `tools/pre-execute`） | 与既有的 `discard` 动词同一类：人在界面上点出来的，没有任何会话请求过它。沙箱守的是会话的写入边界，不是「人点了按钮之后宿主能做什么」；把它塞进会话工具链反而要求每条会话都在创建时承担一次网络动作 |

同一批决定里还有三处取舍，一并记在这里：

- **严格校验**：`baseRef` 的 schema 只接受 `fresh` / `head` 两个字面量，其他值让插件在挂载
  时失败，profile 起不来。拼错时静默退回另一个基点，等于让「我从哪份代码开始」取决于手滑。
- **没有 GUI 控件**：和 `defaultEnabled`、`guardSourceCheckout` 一样，只走 profile 的 patch
  层。一个项目级的默认基点不需要常驻控件，改一次就作用于之后的每一次创建。
- **交接解析后的提交**：fetch 成功后把 `origin/<默认分支>` 解析成 commit id 再交给
  worktree 服务，而不是把 ref 名传下去。这关掉了「另一个进程在 fetch 与 `worktree add`
  之间推进 ref」的窗口，代价是 prepare 的返回里要多带一份「基点从哪来」的紧凑描述，浏览器
  半才知道该不该显示那句提示。

## 后果

- **每个新会话的第一次隔离多付一次网络往返**：远端正常时是几百毫秒，远端不可达时最多多等
  5 秒才落到本地 HEAD。离线可用，但不再「瞬时」。
- **不节流就是重复 fetch**：同一天在同一仓库连开五个会话就是五次。换来的是「fresh 就是
  fresh」这条可解释的承诺——没有一层用户看不见的时间窗需要他猜。
- **基点不再等于「我本地看到的东西」**：未推送的本地提交不会进副本，除非把 `baseRef` 设成
  `head`。这是行为变更而不是纯加法，release note 必须写明。
- **fetch 在主检出上跑**（副本共享同一个 Git 目录），会改写主检出的 `FETCH_HEAD`。依赖
  `FETCH_HEAD` 的脚本、或人工 `git merge FETCH_HEAD`，可能读到一个插件刚拉下来的默认分支。
  这与用户手工 fetch 一次是同类的副作用，不是特权。
- **不复制 Claude Code 的命名与清理**：`git branch` 里没有 `worktree-` 前缀，用
  `git worktree list` 也看不出副本被谁锁着；从 Claude Code 迁过来的用户要重新学一遍
  「副本在哪、谁负责删」。
- **严格校验把拼写错误变成启动失败**：一次启动故障，换来的是不会静默选错基点。错误信息里
  是 `baseRef` 的枚举值，路径明确。
- **没有 GUI 控件**：想改只能编辑 profile 的 patch 层再重启，面板和开关都不提供入口。
- **fetch 绕过会话沙箱**：审计这类动作只能看宿主日志；沙箱不提供任何拦截面，也没有计划提供。

## 考虑过但不选的

- **复刻 24 小时 `FETCH_HEAD` 节流**：能满足「别每次都拉」，但它的可观测语义是「fresh 也可能
  stale」——24 小时内第二次开新会话，副本静默停在旧提交。要省网络宁可把 refspec 收得更窄，
  也不要引入一个用户看不见的时间窗。
- **命名 / 锁 / 清理对齐 Claude Code**（`worktree-<name>`、`git worktree lock`、忽略
  `**/.claude/worktrees/`、复制项目设置、`claude rm` 式清理）：每一条都要在「谁负责删、删不
  干净怎么办」上添一层新语义，而当前的池 + 面板已经能回答这个问题。
- **在面板里显示每份历史副本的基点**：`git worktree list` 不记录分支是从哪里来的，插件也没
  持久化过这件事；要做就得新增一层存储，还要处理「这条历史记录当初没记」的情况。当前只把
  「这次从远端还是本地 HEAD 来」放在开关的 hover 提示里，生命周期只有一次创建。
- **给 `baseRef` 加 GUI 控件**（hero 开关或面板）：一个项目级的逃生门不需要常驻控件；配置层
  的改动作用于之后的每一次创建，与会话内的一次性选择不是同一权限级别。
- **宽松校验、非法值回退**：让手滑决定基点，比一次清晰的挂载失败更难排查。
- **拉全部远端分支、带 tag、`--prune`、浅 fetch**：都超出「给新会话一个足够新的起点」的
  范围，而 `--prune` 会删掉别人正在用的 remote-tracking ref，浅 fetch 会永久浅化仓库。
