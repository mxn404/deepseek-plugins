# 版本默认只 bump patch：对 semver 的有意偏离

旧的发布规则按 semver 直觉分配版本位：修 bug / 行为微调用 `patch`，新功能或新配置用
`minor`。这条规则让每一次「新功能」都自动升 B 位，wire 契约变更与破坏性变更也会被各自的
默认推向 minor/major。维护者要求反过来收紧：**默认只 bump patch（C 位）**，A/B 位只在当次
请求里被明确要求时才改。这与 semver 冲突，所以记在这里，避免下一次又被「新功能应该
minor」的直觉改回去。

## 为什么偏离

本仓的插件各自独立发布，用户经市场安装与更新。这里没有下游包按版本范围依赖这些插件，
minor / major 位不携带任何本仓会兑现的兼容性承诺；版本号实际承担的是发布身份，以及市场
页面「可更新」的比较键。按变更类型自动升 B/A 位，会造出「看起来像兼容性承诺、却没有任何
机制检查」的版本序列，还让版本位取决于写 changeset 的人对「新功能」的判断。默认 patch
让版本序列可预测，需要强调时由维护者显式要求。

## 决定

- **默认 `patch`（C 位）**：修 bug、行为微调、新功能、新配置、wire 契约变更都先用 `patch`
  发。
- **`minor` / `major` 只在当次明确要求时使用**：维护者在一次请求里说要改 B 位或 A 位，才
  改；「这是新功能」或「这是破坏性变更」不构成自动升级的理由，一次要求也只对当次发布有效，
  不是常驻许可。
- **新包首个 changeset 例外**：用 `minor`，`0.0.0` → `0.1.0`，沿用本仓 dsh-new-session、
  dsh-path-rules 从 0.1.x 起的惯例；`0.0.0` 只是 npm 初始化占位，不作为公开版本发布。
- **版本号只由 `changeset version` 写**：不手改 `package.json` 的 `version` 绕过 changeset，
  也不为空补版本位另发一次发布。
- **范围与分工**：规则作用于本仓的插件包，其他仓库与包不受影响。版本位规则写在
  [`.dsh/rules/versioning.md`](../../.dsh/rules/versioning.md)；合并后立刻发版的清单仍留在
  [`.dsh/rules/release.md`](../../.dsh/rules/release.md)。

## 考虑过但不选的

- **严格 semver**：把没有人消费的兼容性承诺变成发布门槛——每个新功能都要 minor、每次
  破坏都要 major，而本仓没有任何范围依赖去验证这个承诺，代价换不来收益。
- **按包单独的策略**（成熟包走 patch、新包走 semver 之类的组合）：会让「版本位是什么
  意思」取决于包名，维护者与 agent 都得先记住每个包的策略；现有包数量不值得这层复杂度。
- **CI / 脚本校验版本位**：规则与发布流程是两个关注点，先靠规则与评审；出现真实漂移再补
  脚本（#33 明确把 CI 校验放在范围外）。
- **用日期或构建号代替版本位**：会与 npm、changesets、市场索引的既有语义脱节，而且标签
  格式 `<包名>@<版本>` 依赖可解析的版本号。
- **让 changeset 类型自动映射版本位**（例如按 PR 标题的 `feat` / `fix` 前缀）：本仓没有这
  套前缀纪律，映射只会退化成猜。

## 后果

- **版本号不再是兼容性承诺**：`0.5.1` → `0.5.2` 不代表「只修了 bug」，`0.5.1` → `0.6.0`
  也不代表「加了功能」；CHANGELOG 是唯一的信息来源。依赖 semver 范围的下游（目前没有）
  可能在破坏性 patch 上踩坑，这是有意接受的代价。
- **破坏性变更可以出现在 patch 位**：将来若出现按范围依赖的消费者，单独给那个包开例外，
  而不是把 semver 默认加回规则层。
- **维护者要升级版本位时必须在当次请求里说清楚**：请求里没说 A/B 位，agent 就只写
  `patch`；不能从「这是新功能」自行推断。
- **新包的起点仍可辨认**：首个 changeset 的 minor 例外让 0.0.0 → 0.1.0，与既有包一致，
  不破坏「0.1.x 起」的惯例。
- **发布流程不变**：patch 发布同样走合并后立刻发、打 `<包名>@<版本>` tag、验证 npm 与
  市场索引的完整清单。
