# 项目级 hooks 不做信任门禁：clone 即信任

`.dsh/hooks.json` 是仓库内容。一个项目级层里的 `command` 会在 session 的 shell 里执行，
`module` 会直接 import 进宿主进程，两者都以用户自己的权限运行。多数 agent 产品会给项目级
配置加一道一次性的信任提示或 allowlist；本插件**不做**。只要有 `.dsh/hooks.json` 且
`projectHooks` 开着，session 一旦在该仓库里跑起来，规则就生效，没有「是否信任此仓库」的
问题。README 把它写成一条设计边界：**clone 即信任**。

## 决定

- 用户级、项目级、local 三层**全部自动发现**，不区分「可信 / 不可信仓库」，也没有首次
  运行的确认。
- 不维护 allowlist、不记录信任决定、不引入项目身份（remote URL、commit、路径）作为键。
- 行配置里的 `projectHooks` / `localHooks` 是**唯一**的开关：关掉即只跑用户级。
- 不提供 sandbox：command 走宿主 `ctx.shell`（执行器负责凭据擦洗与超时/进程组），module
  在宿主进程内。两者都没有文件系统或网络隔离。

## 为什么

- **信任级与仓库代码相同**：agent 在这个仓库里本来就会读 `AGENTS.md`、跑 `pnpm test`、
  执行构建脚本。hooks 是同一批维护者写的同一类自动化。给 hooks 单独加一道门，挡不住真正
  的恶意仓库，只多一次会被习惯性点掉的确认。
- **dsh 目前没有项目信任模型**：宿主按目录工作，不判断仓库是否可信。本插件是 host-only、
  没有 UI，也拿不到跨 session 的持久信任存储。硬造一个「本插件自己的信任表」会变成一份
  用户看不见、也删不干净的状态。
- **仓库级共享是前提**：User Story 1 要求规则随代码提交、团队共享。默认不信任项目配置等于
  把这个前提作废，用户还得为每个 clone 做一次授权。
- **spec 明确不做**：项目级信任审批 / allowlist / sandbox 在 spec 的 Out of Scope 里。
  与其做一个半成品门禁，不如把边界写清楚。

## 后果

- **打开陌生仓库可能执行代码**：`session.start` 的 hook 在第一个模型请求之前就会跑，
  `tool.pre` 的 hook 在第一次工具调用时跑。用户在审阅 `.dsh/hooks.json` 之前，规则已经
  生效。README 与本节都要求用户先看这个文件。
- **没有「这个仓库被批准过」的记录**：每次 session 都按当前文件重新解析。改过的文件下一次
  事件立即生效，不存在缓存的信任决定。
- **审计能定位来源**：每次运行写 `source`（配置文件绝对路径）与 `hook_id`。事后能看出是哪
  一层、哪一条跑了；但审计不能阻止运行。
- **关掉 projectHooks 是唯一防线**：`localHooks` 同理；用户级文件仍生效。关掉后项目规则
  完全消失，不会以「未信任」的名义半开。
- **两个执行面风险不同**：command 至少经过 shell 执行器的超时、进程组终止与凭据擦洗；
  module 是进程内普通 JS，能与插件、宿主共享权限（见 README 的「已接受的盲区」）。

## 如果重新考虑，会改什么

- dsh 若引入项目信任模型，本插件应该复用它，而不是自建：信任键用宿主认的项目身份，项目
  规则默认不跑，直到用户批准。
- 若本插件将来有 UI 或持久化通道，可以做「每仓库一次确认 + 记住决定」，默认拒绝；这需要
  一个跨 session 的存储位置与一个可撤销的入口。
- 更根本的替代是 sandbox：把 command 与 module 放进受限进程/worker，按能力授权文件与网络。
  module 的活 agent/session API 会因此受限，需要重新设计策展面。

## 考虑过但不选的

- **默认关闭项目层，用户显式开启**：安全，但违背「clone 下来团队规则就生效」的产品前提；
  每个开发者都要重新配置一次。
- **只允许 builtin、禁止 command/module**：`deny` / `context` 能覆盖一部分规则，但
  formatter、测试、脱敏这些真正需要脚本的场景全部落空，本插件退化成一张静态规则表。
- **按 remote URL + commit 做 allowlist**：同一仓库的不同 commit 都能改 hooks，钉 commit
  等于每次提交都要重新授权；而且本地路径仓库没有 remote。收益低、复杂度高。
- **在插件里跑一个自建 sandbox**：宿主已经提供了 shell 执行器与进程模型，插件再套一层
  沙箱既不可靠也超出范围；真正的隔离应该由宿主提供。
